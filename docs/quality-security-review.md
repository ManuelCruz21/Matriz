## F01 — responsible-ID validation fix and focused evidence (2026-11-15)

**F01 addressed for parsed numeric integrality/range; focused tests passed.** Reinspection found that the current working tree already had a `doubleValue() != longValue()` guard in `TaskController.ids`, contrary to the earlier review's description of unconditional truncation. Ordinary `1.9` was therefore already rejected; the prior review overstates that current behavior. The floating-point comparison could nevertheless accept out-of-range numbers through rounding (for example `9223372036854775808.0` comparing equal to the double representation of a saturated long). This record corrects the earlier review rather than claiming the ordinary fractional case was newly reproduced.

Minimal production change at `backend/src/main/java/pt/matriz/tasks/TaskController.java:177–189`: replace the floating-point comparison/conversion with `new BigDecimal(number.toString()).longValueExact()`, rejecting non-integral, non-positive and out-of-long-range parsed numeric values before eligibility checks or writes. Both creation and responsible replacement use this shared parser. Integer-valued decimal `2.0` remains accepted; existing valid integer IDs remain unchanged, including values beyond double's exact integer precision and Long.MAX_VALUE. No authorization/schema/policy change or unrelated fix.

Added three focused parameterized methods in existing `backend/src/test/java/pt/matriz/tasks/TaskControllerTest.java`:

- `responsibleIdsRejectInvalidNumbersWithoutWrites`: **6** creation cases (`1.9`, `2.5`, `-1.5`, `0`, `9223372036854775808`, `9223372036854775808.0`), each following a valid first ID in the list. Assert **422**, responsibleUserIds error and exactly identity/membership reads; `verifyNoMoreInteractions(jdbc)` excludes eligibility reads, task INSERT and all dependent writes.
- `responsibleReplacementRejectsInvalidNumbersWithoutWrites`: **3** replacement cases (`1.9`, `2.5`, `9223372036854775808.0`), assert the same **422** field error and only identity/task-access reads, with no further JDBC interaction/deletion/assignment/history writes.
- `responsibleIdsPreserveValidIntegers`: **5** creation cases (`2`, `2147483648`, `9007199254740993`, `9223372036854775807`, `2.0`); assert **201** and exact long values passed to eligibility and assignment INSERT. JDBC is mocked; these are controller-boundary evidence, not real DB persistence.
